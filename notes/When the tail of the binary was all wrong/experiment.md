# Training Run: Minimal Static Binaries (Returns Dataset)

**Date:** 2026-03-06
**Model:** Qwen3-0.6B with QLoRA
**Dataset:** 10,000 minimal static binaries (returns 1-10000)
**Training time:** ~3 hours

---

## Summary

We trained a 0.6B parameter model to generate RISC-V binaries from natural language prompts. **Result: Partial success.** The model learned the ELF binary structure perfectly (headers, segments, syscall sequences) but failed to encode the correct value - generating a binary that returns 145 instead of 42 when prompted "Write a program that returns 42".

**What worked:** Structure learning (✅ valid ELF, ✅ correct instruction pattern, ✅ no hallucination)
**What didn't:** Value encoding (❌ wrong immediate value in instruction)
**Key insight:** Pattern recognition works, but semantic grounding (text "42" → machine code for 42) is hard.

**Next:** Systematic evaluation across value ranges to understand error distribution and test hypotheses about why the mapping failed.

---

## The Experiment

After an initial failed attempt with large dynamically-linked binaries (8KB each, too complex), we switched to minimal static binaries (~850 bytes) and rebuilt the entire dataset. This is the second training attempt. The question: **Can a 0.6B parameter language model learn to generate executable RISC-V binaries directly from natural language prompts?**

### Training Configuration

```
Dataset: 10,000 examples
- Prompts: "Write a program that returns N" (N ∈ [1, 10000])
- Binary format: Minimal static ELF (848 bytes, ~1696 hex chars)
- Context window: 2048 tokens (vs 32K max)

Model: Qwen3-0.6B with QLoRA
- LoRA rank: 16, alpha: 16
- 4-bit quantization
- Batch size: 4 (gradient accumulation)
- Learning rate: 2e-4
- Epochs: 3
- Hardware: Single GPU, ~3.2GB VRAM peak
```

### What the Model Needs to Learn

Each binary is 848 bytes of precise structure:

- **ELF header** (64 bytes) - File identification, entry point, offsets
- **Program headers** (168 bytes) - Memory layout, 3 segments
- **Code section** (12 bytes) - The actual RISC-V instructions:

  ```asm
  li a7, 93      # Syscall number (exit)
  li a0, <N>     # Exit code (the value to return)
  ecall          # Make syscall
  ```

- **Metadata** (604 bytes) - Exception handling, compiler info, ISA flags, section headers

The challenge: 98.6% is boilerplate, 1.4% is the actual logic. The model must learn both.

## Analysis

### What Worked ✅

1. **Structure learning:** Model learned the ELF format remarkably well
   - Correct magic bytes: `7f 45 4c 46`
   - Correct architecture: RISC-V (0xf3)
   - Correct entry point: `0x100e8`
   - Valid program headers with proper flags and alignment

2. **Instruction sequence:** Model generated the correct syscall pattern
   - `li a7, 93` - Load syscall number
   - `li a0, <value>` - Load argument
   - `ecall` - Execute syscall

3. **No hallucination:** All generated bytes follow valid ELF structure (no random gibberish)

### What Didn't Work ❌

1. **Value encoding:** Generated 145 instead of 42
   - Instruction format is correct (`li a0, <imm>`)
   - But immediate value is wrong
   - **Hypothesis:** Model hasn't learned the mapping from prompt text → RISC-V immediate encoding

2. **Incomplete generation:** Only produced 54% of binary
   - Stopped at position 461/848 bytes
   - Hit a stopping condition too early
   - **Hypothesis:** Newline in training data or uncertainty threshold

3. **Zero padding:** Filled remaining context with zeros
   - Generated ~4100 chars total (including 3179 zeros)
   - **Hypothesis:** No explicit stopping token, kept generating until max_tokens

## Deep Dive: The Value Encoding Problem

The prompt says "returns 42", which should encode as:

**Decimal 42 → Hex 0x2a → RISC-V immediate:**

```
li a0, 42  =  addi a0, x0, 42
            =  0x02a00513 (32-bit instruction)
            =  13 05 a0 02 (little-endian bytes)
```

**What the model generated (145):**

```
li a0, 145 =  addi a0, x0, 145
            =  0x09100513
            =  13 05 10 09
```

The model got:

- ✅ Opcode correct: `13` (ADDI)
- ✅ Destination register: `05` (a0)
- ❌ Immediate field: `10 09` instead of `a0 02`

### Why This Might Happen

1. **Insufficient training:** 3 epochs over 10K examples may not be enough
2. **Text → number mapping:** Model needs to learn "42" (text) → 0x2a (hex) → RISC-V encoding
3. **Distribution bias:** Value 145 might appear more in training or be a "default" the model learned
4. **Attention to prompt:** Model might not be focusing on the number in the prompt

## Instruction Encoding Deep Dive

For readers unfamiliar with RISC-V:

**RISC-V I-type instruction format (addi):**

```
 31        20 19   15 14  12 11    7 6      0
[  imm[11:0] ][ rs1  ][f3 ][ rd   ][opcode ]
   12 bits     5 bits  3b   5 bits  7 bits

For: addi a0, x0, 42
  imm[11:0] = 42 (0x02a)
  rs1       = 0  (x0 = zero register)
  funct3    = 0  (ADDI)
  rd        = 10 (a0 register)
  opcode    = 0010011 (OP-IMM)
```

**Encoding step-by-step:**

```
imm:    000000101010 (42 in 12 bits)
rs1:    00000        (x0)
funct3: 000          (ADDI)
rd:     01010        (a0 = register 10)
opcode: 0010011      (OP-IMM)

Combined: 000000101010_00000_000_01010_0010011
        = 0x02a00513

Little-endian bytes: 13 05 a0 02
```

The model needs to learn this entire encoding pipeline from text prompts.

## Compression Analysis

Some values use compressed instructions (RVC extension):

**For small values (1, 2, etc.):**

```
li a0, 1  =  0x4505 (compressed, 2 bytes)
             Binary: 0100 0101 0000 0101
             ├─ funct3: 010 (C.LI)
             ├─ imm[5]: 0
             ├─ rd: 01010 (a0)
             ├─ imm[4:0]: 00001 (value: 1)
             └─ op: 01
```

**For larger values (42, 145, etc.):**

```
li a0, 42  =  0x02a00513 (uncompressed, 4 bytes)
```

The compiler chooses automatically based on value range. The model must learn both encodings.

## Hypotheses for Wrong Value

### Hypothesis 1: Insufficient Semantic Understanding

**Theory:** Model treats this as a pattern-matching task, not semantic understanding.

**Evidence:**

- Correct structure (shows pattern learning)
- Wrong specific value (shows lack of semantic grounding)

**Test:** Try values that appear frequently vs rarely in training set.

### Hypothesis 2: Prompt Format Issue

**Theory:** Model doesn't parse "returns 42" correctly.

**Current format:**

```
### Instruction:
Write a program that returns 42

### Response:
<hex binary>
```

**Possible issues:**

- "returns" is ambiguous (could be return statement, exit code, output)
- Number parsing: "42" (text) vs 42 (integer) vs 0x2a (hex)

**Test:** Try different prompt formats:

- "Write a program that exits with code 42"
- "Generate a RISC-V binary that returns 42"
- "Create an executable that exits with value 42"

### Hypothesis 3: Value Distribution Bias

**Theory:** Training data has uneven distribution of values.

**Check:** Analyze if 145 appears more frequently or has special significance.

**Test:**

- Generate for multiple values (1, 10, 42, 100, 1000)
- Check if model always generates same value
- Look for patterns in error distribution

### Hypothesis 4: Attention to Numeric Tokens

**Theory:** Tokenizer or attention mechanism doesn't focus on numbers in prompt.

**Evidence needed:**

- Attention visualization on prompt tokens
- Tokenizer analysis of how "42" is encoded

**Test:**

- Try prompts with emphasized numbers: "returns **42**" or "returns 42 (forty-two)"
- Check if tokenization of numbers is consistent

## Reflections

### What This Tells Us About LLMs and Binary Generation

**Promising signs:**

- LLMs can learn structured formats (ELF)
- Pattern recognition works for boilerplate
- Correct instruction sequences show understanding of assembly structure

**Challenges:**

- Semantic grounding (text → numeric values) is hard
- Precision matters (one wrong byte = wrong behavior)
- Generation length control needs work

**Comparison to code generation:**

- Code generation: semantic → syntax → text (human-readable)
- Binary generation: semantic → syntax → machine code (no human buffer)
- Binary generation has zero tolerance for errors

### The 80/20 Rule Inverted

In typical ML: 80% of results from 20% of effort.

Here: Model got 80% of structure right, but the 20% (correct value) determines success.

**Why?**

- Executables are "digital cliffs" - small changes = total failure
- No partial credit for almost-correct binaries
- This is closer to formal methods than typical ML fuzzy tasks

### Learning vs Memorization

The model clearly learned *something*:

- It's not just memorizing training examples (145 doesn't appear for "returns 42")
- It generated valid ELF structure not in training set exactly
- But it hasn't learned the *mapping* from prompt semantics to encoding

This suggests the model learned:

- ✅ ELF format rules
- ✅ Instruction sequence patterns
- ❌ Semantic meaning of prompt numbers
- ❌ How to encode specific values

## Conclusion

**First training run result: Partial success.**

The model learned the structure of RISC-V ELF binaries remarkably well, generating valid executables with correct syscall sequences. However, it failed to encode the specific value from the prompt, generating 145 instead of 42.

This is both encouraging (structure learning works) and concerning (semantic grounding is hard). The path forward involves systematic evaluation, prompt engineering, and potentially curriculum learning to teach value encoding explicitly.

**Key insight:** Teaching an LLM to generate binaries isn't just about patterns - it's about teaching semantic meaning → machine encoding mapping. That's the hard part.
